# Codebase Map

> Maintained by Cartographer. Updated at each /dock.

## Modules

### CLI Entry & Commands

**Path:** `src/index.ts`, `src/commands/`

Three CLI commands wired up via commander: `init` (interactive scaffold), `upgrade` (regenerate managed files into an existing project), and `config` (interactively change mode/workflow). `src/commands/init.ts` is the most important file — it drives the user-facing prompts via `@clack/prompts` and calls the scaffold orchestrator. `src/commands/upgrade.ts` now includes `migrateLegacyFiles()` that automatically moves old config files from `.claude/` to `.tiller/` on first upgrade (e.g., `.claude/.tiller.json` → `.tiller/tiller.json`, `.claude/TILLER.md` → `.tiller/TILLER.md`, `compass.md` → `.tiller/compass.md`), ensuring backward compatibility when upgrading older projects.

### Scaffold Orchestrator

**Path:** `src/scaffold/index.ts`, `src/scaffold/types.ts`, `src/scaffold/tiller-manifest.ts`

Writes all files into the target directory in a single `scaffold()` call, then handles git init and initial commit. `tiller-manifest.ts` defines `MANAGED_FILES` and `TILLER_VERSION` — the canonical list of what Tiller owns and is responsible for regenerating on upgrade. `MANAGED_FILES` lists `.tiller/TILLER.md` (Tiller-managed config), `.tiller/tiller.json` (manifest), and `.tiller/tech-debt.json`, but not `.claude/CLAUDE.md` (user-owned); the upgrade command guards against deleting user-owned files. Start here when adding or removing any generated file.

### File Generators

**Path:** `src/scaffold/` (flat files), `src/scaffold/skills/`, `src/scaffold/hooks/`, `src/scaffold/agents/`

Each generator is a pure function that returns a string — the content of a file to be written into the scaffolded project. Skills (`sail`, `anchor`, `dock`, `recap`, `setup`, `scout`, `tech-debt`, `repair-hull`) produce `.claude/skills/*/SKILL.md`. The sail skill is the most complex: its Step 2 branch routing selects a `fix/` or `feature/` prefix based on keywords in `$ARGUMENTS`, then handles four chaining cases (related → stay, unrelated → new branch, uncertain → ask, no-args → continue or list). Step 2.7 runs a requirements interview before planning — it gathers scope, behavior, edge cases, and acceptance criteria via a mix of structured and freeform questions, with additional technical topics in detailed mode; the interview is skipped when continuing existing work or when the user opts out. Its Step 3 plan block uses a rigid template to ensure consistent milestone breakdown and decision documentation; the template includes an "Execution rules" section that embeds the full Quartermaster→Captain PASS/FAIL/ESCALATE review protocol inline so the plan is self-contained after a context clear. Step 3 is marked ⚠️ REQUIRED to enforce the no-skip policy on planning. Step 2.7 is marked ⚠️ REQUIRED to enforce requirements gathering. Step 4.5 is marked ⚠️ REQUIRED to enforce the code review step. **Step 3.5** evaluates scope complexity using heuristics (milestone count, file count, subsystem count) to classify work into Small / Medium / Large tiers: in simple mode, evaluation happens silently; in detailed mode, the sail announces the tier and waits for user confirmation or override. Step 4 restructures execution into three tier-specific paths: **Small tier** (solo sequential, no agent spawning) for < 3 milestones with < 5 files in a single subsystem; **Medium tier** (parallel with lead participation) uses TeamCreate + TaskCreate for independent milestones while the lead also implements, then continues with sequential milestones; **Large tier** (orchestrator mode) delegates ALL implementation to spawned workers selected by milestone complexity (haiku for mechanical tasks, sonnet for standard features, opus for complex architecture), with the orchestrator doing incremental commits and compass updates only after each worker completes. Step 4 also reads and updates `.tiller/compass.md` throughout the sail — the compass tracks branch context, progress through the vibe-loop stages (Orientation, Planning, Execution, Testing, Quartermaster review), and a live milestone checklist; in detailed mode the sail creates compass.md on first run, updates it as each milestone completes, checks off stages before code review, and adds completion notes. `tech-debt.ts` and `repair-hull.ts` now include workflow-aware step branching: in solo workflow they merge chore branches locally (Step 4 reads workflow config and does direct merge with --no-ff), while in team workflow they push the branch, attempt to open a PR via `gh pr create --fill`, and fall back to manual PR instructions if gh is unavailable. The `anchor` skill now includes Step 6 (Code Review ⚠️ REQUIRED) that spawns the Quartermaster to review the feature branch diff; it follows the same PASS/FAIL/ESCALATE protocol as sail Step 4.5, allowing one round of negotiation before escalating to the Captain on impasse. Hooks (`post-write`, `secret-scan`, `session-resume`, `plan-context`) produce `.claude/hooks/*.sh`. `session-resume.sh` runs on SessionStart(clear) to detect feature/fix branches and prompt the user to read `.tiller/compass.md` if it contains active sail progress. `plan-context.sh` is a SubagentStart hook that runs when the Plan agent starts; it injects the /sail Step 3 plan template and current `.tiller/compass.md` state via additionalContext, ensuring Plan agents know the rigid template structure and have visibility into vibe-loop progress. Agents (`quartermaster`, `bosun`, `captain`, `cartographer`) produce `.claude/agents/*.md` with native Claude Code frontmatter (`name`, `description`, `model`, `tools`) and spawn via `subagent_type` rather than custom Task wiring. The cartographer agent maintains only the Modules section of `codebase-map.md`; shipped feature history is tracked exclusively in `changelog.md`. `claude-md.ts` covers the two CLAUDE.md-family files: `generateUserClaudeMd()` produces the user-owned `.claude/CLAUDE.md` (a single import line pointing at `.tiller/TILLER.md`), and `generateTillerMd()` (formerly `generateDotClaudeMd`) produces the Tiller-managed `.tiller/TILLER.md` that holds all vibe-loop rules; it now begins with a "Protocol enforcement" section that explicitly mandates step execution without skipping or reordering, supporting the no-skip markers in skills. The "Workflows" section in `.tiller/TILLER.md` now documents the team workflow behavior: tech debt chore branches are pushed and opened as PRs instead of merged locally. This split means upgrades regenerate only `.tiller/TILLER.md` and never clobber user edits in `.claude/CLAUDE.md`. `compass.ts`, `changelog.ts`, `gitignore.ts`, `settings-json.ts`, and `tech-backlog.ts` cover the remaining generated files. `compass.ts` is a template for the gitignored local waypoint file (`.tiller/compass.md`); `gitignore.ts` maintains the canonical `TILLER_GITIGNORE_ENTRIES` list (`.tiller/compass.md` and `.tiller/local.json`) and is used by both init and upgrade to ensure entries are present.

### Utilities

**Path:** `src/utils/`

Thin wrappers over Node built-ins. `fs.ts` provides `writeFile` (with auto-mkdir) used by the scaffold orchestrator. `git.ts` wraps `isGitRepo`, `gitInit`, `gitAdd`, and `gitCommit` for the post-scaffold commit. These two files are the only place I/O primitives should be imported directly.

### Test Suite

**Path:** `test/`

Vitest unit and integration tests. Unit tests cover individual generators; integration tests scaffold into a temp directory and assert the resulting file tree and content. Run with `npm test`. The `npm run regen` command (build → link → `tiller-ai upgrade --yes`) regenerates Tiller-owned files in the package itself by running upgrade on the built version; this replaces the old `scripts/regen-skills.ts` helper.

### Promotional Website

**Path:** `website/`

Static Astro site deployed to GitHub Pages. Nautical theme with navy/teal/gold palette. Not part of the npm package — exists purely for project marketing. The landing page is assembled from section components in `website/src/components/` (Hero, Problem, Features, WaysToWork, HowItWorks, GettingStarted, Footer). The WaysToWork component showcases three personas (Solo Creator using simple mode, Solo Developer and Engineering Team using detailed mode) with feature cards explaining how Tiller supports each workflow. Edit those components for content changes; the GitHub Actions pipeline handles deployment.
